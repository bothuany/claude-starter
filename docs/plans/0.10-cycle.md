# 0.10: a named cycle with small contexts and a durable plan file

## Why

In the author's own session logs, the main session's own steps are most of the re-read volume, and
most of that is spent in a large context. The routing layer added in 0.9.x (role policy, lead edit budget,
`/solo`) keeps one long lead session alive. 0.10 replaces it with a cycle that is started for one piece of work and
hands off through a plan file, so the build and the reviews start in a clean context.

## Decisions (settled with the user; do not reopen)

- The cycle is **off by default** and started per piece of work with `/starter:cycle <work>`. Questions and small
  fixes never enter it. Always on: the ask and verify rules, and the review gate.
- Phases: gather → plan → plan-review → build → code-review → probe, then `done`.
- `writer` (Sonnet, high) builds from the plan file. `reviewer` (Opus, medium) reviews the plan, then the code.
  `reader` (Sonnet, medium) does wide reading. A named role is used, never a fork: a fork inherits the lead's context.
- Removed: fan-out and its workflow, `locator`, the lead edit budget, `/solo`, the old `/subagents` pane,
  `diff-walkthrough`.
- New pane: one line of stations on top, a card for the running phase, finished phases with their evidence below.

## Contract: the plan file

`docs/plans/<slug>.md`, at most about 150 lines. The cycle skill, the writer and the pane all read it by these rules.

- Front matter: `cycle` (the slug; a file without it is not a cycle plan), `phase`, `branch`, and `waiting: user`.
  Only the lead edits the front matter.
- `phase` is one of `gather`, `plan`, `plan-review`, `build`, `code-review`, `probe`, `done`. The pane shows the
  first six as stations and `n/6`, where n is the position of the current phase; `done` shows 6/6, all filled.
- `waiting: user` sits on the current phase while it cannot finish without the user's answer (after the reviewer's
  pass in `plan-review`, or wherever a decision is needed). The lead removes it when the user has answered.
- `## Items`: one line `- [ ] N. <text>` per item; the text may continue on indented lines. The item's check is the
  first indented line that starts with `check:` before the next item. The command is what follows `check:`, with one
  pair of surrounding backticks removed. It runs in bash from the repository root (Git Bash on Windows) and passes
  when it exits 0. `- [x]` and `- [X]` both count as ticked. CRLF line ends and a BOM are tolerated.
- The writer ticks an item only after its check passes.
- `## Log`: the lead adds one line `- <phase>: <evidence>` when it moves the phase on. The pane prints the lines as
  they are. Stopping a cycle sets `phase: done` and logs `- off: stopped at <phase>`.

## Risks

- The pane depends on mod APIs (store, file reads, pane open) that only the `plugin-authoring` skill documents; the
  writer must read it before item 12, not guess.
- `rules.md` and the cycle skill steer the model, so their wording is judgement: the lead reads both diffs in full.
- Whether a user-only skill's text survives a context compaction is unverified; resuming with `/starter:cycle` and
  re-reading the plan file at every phase are the guard.
- Removing skills breaks `/starter:fan-out` and `/starter:diff-walkthrough` for anyone who uses them.
