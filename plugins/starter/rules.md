## Working rules (claude-starter)

**Ask before assuming.** When a request is ambiguous in a way that changes the outcome, and the code, docs or conversation can't settle it, ask with AskUserQuestion before writing: at most 4 questions at once, your recommended option first. Don't ask what you can look up, and don't ask for permission to do what was clearly requested. Subagents can't ask the user, so settle open questions before you delegate.

**Check the docs, not your memory.** Before writing code against a third-party library, framework, SDK or CLI whose API may have changed, look it up with the context7 MCP (or the official docs). Say which version you checked.

**Web research.** If the obscura MCP is connected, use it first: open your own tab, search through `https://html.duckduckgo.com/html/?q=<query>`, and read pages as markdown. Fall back to WebSearch and WebFetch when obscura is missing or fails, and say so.

**Delegate to keep the main context clean.**
- The main session plans, delegates and checks; it never writes or edits code itself, however small the change. Implementation goes to a subagent, one writer per repository at a time, and the check goes to a fresh subagent that didn't write it. Batch small fixes into one brief for the same writer instead of one subagent per fix.
- Wide searches and reading many files go to a subagent (Explore) that returns conclusions, not file dumps.
- For an approved plan with 3 or more parts, you may suggest the `starter:fan-out` skill: its workflow builds the plan outside the main session (one Sonnet builder, parallel workers only for very large plans) and reviews it once. Start it only after the user agrees; otherwise hand the plan to one writer subagent.
- A subagent brief is self-contained: the goal, the files it owns, the contract it must follow, what "done" means and how to check it. Read the diff a worker produced; don't trust its summary.

**Verify before you say done.** Run the project's own checks (tests, type check, lint) that cover what you changed and report failures verbatim. When a change touches 2 or more non-test files with at least 15 changed lines in total, changes more than 50 non-test lines, or touches security, data handling or concurrency (not counting docs-only, rename or formatting changes), and the fan-out review didn't already cover it, call the `code-review` skill with the Skill tool (args: the effort the repository's `REVIEW.md` gives this change's risk tier; `medium` when there is no `REVIEW.md` or the tier is unclear), wait for its findings before your final message, and handle each finding with evidence: reproduce it (a command or a throwaway test), then fix it; dismiss it only with the line you read or a command you ran; report it as unverified only when checking would take more than a few minutes or needs the user's decision. "The task's examples pass" and "it was like that before" are not evidence. If the repository has a `REVIEW.md`, read it before a review and judge the findings by it; a change it puts in its lowest tier needs no review beyond the project's checks, and one in its highest tier is also named to the user as needing a person to read it. Review has to converge: after the first review of a change, re-review only the new diff and never repeat a settled finding; when a finding is one of a class, fix every instance in the change; report a bug the change did not introduce as pre-existing and leave it; after three review rounds on the same change, stop and ask the user whether the approach is right. Skipping it then needs a reason you state; below that threshold, skip it without comment. Say plainly what you did not verify.
