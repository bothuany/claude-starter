## Working rules (claude-starter)

**Ask before assuming.** When a request is ambiguous in a way that changes the outcome, and the code, docs or conversation can't settle it, ask with AskUserQuestion before writing: at most 4 questions at once, your recommended option first. Don't ask what you can look up, and don't ask for permission to do what was clearly requested. Subagents can't ask the user, so settle open questions before you delegate.

**Check the docs, not your memory.** Before writing code against a third-party library, framework, SDK or CLI whose API may have changed, look it up with the context7 MCP (or the official docs). Say which version you checked.

**Web research.** If the obscura MCP is connected, use it first: open your own tab, search through `https://html.duckduckgo.com/html/?q=<query>`, and read pages as markdown. Fall back to WebSearch and WebFetch when obscura is missing or fails, and say so.

**Delegate to keep the main context clean.**
- The main session plans, delegates and checks. It makes a small, targeted fix itself (roughly under 30 changed lines); a larger rewrite or wide reading goes to a subagent. Pick the subagent by the type of task: `locator` finds and lists, `reader` reads and reports, `writer` changes files, `reviewer` checks a change it didn't write, in a fresh context. Reading many files or a wide search goes to `reader` (or the built-in Explore), which returns conclusions, not file dumps. Each role fixes its own model and effort, so don't set them yourself, except when escalating (below).
- Orchestrate, don't queue: independent pieces of work run at the same time. Give each independent piece its own `writer`, in parallel; every brief names the files it owns, and no two running writers own the same file (pieces that share a file go to one writer, or run one after the other). Start the review of a finished piece while other pieces are still being written. Batch small fixes that touch the same files into one brief instead of one subagent per fix.
- In work judged by eye (UI, layout, styling), the subagent only applies the change; the main session compares before and after itself.
- A task that fits no role (design, planning, research, anything else) goes to a general-purpose subagent with its own brief; you choose its model and effort and say why in one line. Judgement, design, planning: the session's model, high effort. Research, wide reading: medium effort or more; a cheaper model only if the result is easy to check. Exact-rule mechanical work: low effort or a cheaper model. Independent research topics: one subagent each, in parallel.
- Escalation is per task, not per session: only the re-send of the failed brief gets the higher tier; every new task goes to its role as defined, with no `model` or `effort` set, even right after an escalation. When a result fails (checks fail twice, a serious reviewer finding, or a clearly wrong or incomplete answer), step up by role: `writer`, re-send with `model: "opus"`; `locator`, ask `reader`; `reader`, re-send with `effort: "high"`; `reviewer`: don't retry; tell the user. Say in one line which task you escalated and why.
- For an approved plan with 3 or more parts, you may suggest the `starter:fan-out` skill: its workflow builds the plan outside the main session (one Sonnet builder, parallel workers only for very large plans) and reviews it once. Start it only after the user agrees; otherwise split the plan into independent parts, one writer each.
- Keep a Workflow under about 10 agents: past 10–20 agents the extra ones repeat each other's work, and merging their reports costs more than they add. Go bigger only when the user asks for that scale in the prompt.
- A subagent brief is self-contained: the goal, the files it owns, the contract it must follow, what "done" means and how to check it. Read the diff a worker produced; don't trust its summary.

**Verify before you say done.** Run the project's own checks (tests, type check, lint) that cover what you changed and report failures verbatim. Independent review is for risky code only: when a change touches the network, permissions or stored data (not counting docs-only, rename or formatting changes), and the fan-out review didn't already cover it, send the change to the `reviewer` subagent, which reads `REVIEW.md` and runs the `code-review` skill at the effort `REVIEW.md` gives this change's risk tier (`medium` when there is no `REVIEW.md` or the tier is unclear); call the `code-review` skill yourself with the Skill tool, with that effort as args, only when no reviewer agent is available. Wait for the findings before your final message, and handle each finding with evidence: reproduce it (a command or a throwaway test), then send the fix to the writer; dismiss it only with the line you read or a command you ran; report it as unverified only when checking would take more than a few minutes or needs the user's decision. "The task's examples pass" and "it was like that before" are not evidence. If the repository has a `REVIEW.md`, read it before a review and judge the findings by it; a change it puts in its lowest tier needs no review beyond the project's checks, and one in its highest tier is also named to the user as needing a person to read it. Review has to converge: after the first review of a change, re-review only the new diff and never repeat a settled finding; when a finding is one of a class, fix every instance in the change; report a bug the change did not introduce as pre-existing and leave it; after three review rounds on the same change, stop and ask the user whether the approach is right. Skipping the review of a risky change needs a reason you state. Any other change needs none: for one that only changes how something looks, the tests and a side-by-side check of before and after are enough, and when the review gate asks about a change that is not risky, say so in one line and stop. Say plainly what you did not verify.
